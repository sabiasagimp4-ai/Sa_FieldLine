# YMM4 本実装（Direct2D）の設計メモ

プロトタイプで確定した挙動を Direct2D カスタムエフェクトへ移植した結果の記録。
Sa_chromablur と同じ構成（`IVideoEffectProcessor` + `D2D1CustomShaderEffectBase`
+ fxc でビルドした `.cso` を埋め込み）を踏襲している。

移植の基準は `prototype/gpu_sim.py`。これは **GPU で書ける演算だけ**で
リファレンス（`prototype/fieldline.py`）を再現したもので、HLSL は
このファイルの式をそのまま写している。数式を変えるときはまず gpu_sim を直し、
`tests/gpu_pipeline_regression.py` で見た目が変わらないことを確かめること。

---

## 単一パスでは無理なので、パスを分ける

「広域拡散 → 場の確定 → 流線積分 → 引き伸ばしの伝播」で必要な近傍サイズが全く違う。

| パス | シェーダ | 解像度 | 入力 | 出力 |
| --- | --- | --- | --- | --- |
| P0 | `Luma` | 等倍 | 元画像 | R = 輝度 |
| P1 | `Edge` | 等倍 | σ,2σ,4σ,8σ,16σ でぼかした輝度 (5) | RG = 法線(折込), B = エッジ強度 |
| — | `Stats` | 1/2 | Edge / Spread | (x², 1) |
| P2 | `Confidence` | 等倍 | Edge, 全画面RMS | RG = conf·n(折込), B = conf, A = 強さ×conf |
| P3 | `Spread` | 1/2 | R/32〜R でぼかした conf·n (6) | RG = V(折込), B = φ |
| P4a | `FieldDir` | 1/2 | Spread, 全画面RMS | RG = v(折込) |
| P4b | `FieldA` | 1/2 | 平滑化した v | RG = 向き, B = 歩幅ゲート, A = curl |
| P4c | `FieldB` | 1/2 | 平滑化した v, Spread, RMS | R = amp, G = φ, B = res |
| P5 | `Radial` | 1/2 | FieldB | RG = 外向きの単位ベクトル |
| P6 | `Advect` | 等倍 | 元画像, FieldA, FieldB | 変位サンプリングした色 |
| P7a | `Priority` | 等倍 | Confidence, それを帯幅でぼかしたもの, 全画面平均 | R = 優先度 |
| P7b | `StretchInit` | 等倍 | 変位後の色, Radial, 優先度 | RGB = 運ぶ色, A = スコア |
| P7c | `StretchStep` ×N | 等倍 | 直前のパス, Radial | 同上（1 歩ぶん伝播） |
| P7d | `Composite` | 等倍 | 変位後の色, 伝播結果 | 不透明で上書き |
| P8 | `Post` | 等倍 | 合成色, FieldA, FieldB, 元画像 | 発光 / 力線 / 元画像を残す |

長距離拡散を縮小した解像度でやるので、**`Radius` を上げてもコストがほとんど増えない**。

解像度は下げすぎると眠くなる。3 倍に拡大して比べた結果:

| | 1/4 | 1/2 | 等倍 |
| --- | --- | --- | --- |
| 場 | 曲がりを上げた時の細部が溶ける | ほぼリファレンス通り | ごくわずかに勝る |
| 引き伸ばしの伝播 | 論外 | 帯の境界も運ぶ色も眠い | リファレンス通り |

場は **1/2**、伝播は **等倍**にした。伝播を 1/2 にすると 1 パスのコストは 1/4 だが、
運ぶ色そのものが半分の解像度になるので、帯の中のディテールが戻らない。

## リファレンスから変えた所と、その理由

### 1. percentile 正規化 → 全画面 RMS

リファレンスは `np.percentile(|x|, 99)` で正規化している。GPU では並べ替えができない。

代わりに **`(x², 1)` を出すパスを作り、`Scale(0.5)` を 1x1 になるまで重ねて**
全画面平均を求め、`sqrt` を取って RMS にする。`Scale(0.5)` の線形補間は
ちょうど 2x2 の箱平均になるので、これは厳密な平均。

1x1 の結果は `Border(Clamp)` で無限に広げるので、どの位置で読んでも同じ定数が返る。
読む側は座標を気にしなくてよく、CPU への読み戻し（＝同期待ち）も要らない。

percentile と RMS の比は `K_MAG` 等の定数で吸収する。値は
`prototype/gpu_sim.py` の頭と `Shaders/FieldLineCommon.hlsli` の両方にあり、
**必ず一致させること**。

正規化が要るのは 3 つで、いずれも**比（percentile ÷ RMS）**として持つ。
文字のような輪郭がまばらな素材まで含めて測っても、比はそこそこ安定している。

| 定数 | 何を正規化するか | 実測の幅 |
| --- | --- | --- |
| `K_MAG` | エッジ強度 | 3.39 – 4.17 |
| `K_PHI` | 輪郭密度 φ | 1.55 – 2.64 |
| `K_COH` | 場の強さ \|v\| | 2.57 – 3.91 |

> **絶対値を定数にしてはいけない。** `K_COH` を最初「写真で測った
> `p99(|v|)` の値」そのものにしていた。写真では合うが、**文字に掛けると
> 効果が丸ごと沈む**。輪郭がまばらで場全体が弱いので、固定の分母では
> コヒーレンスが上がらない。比にして RMS で割れば素材を選ばない。

> **局所ぼかしで正規化してはいけない。** 一度 `blur(x², 大きいσ)` で試したが、
> 平坦な領域ほど分母が小さくなり、そこだけ効果が最大になる。
> 結果は画面全体が均等にぐにゃぐにゃ歪む、まさに避けたかった絵になった。

### 2. 符号つきの値は [0,1] に折り込む

法線・ベクトル場・curl は負になる。中間バッファが 8bit しか取れない環境だと
潰れて場が壊れるので、`SA_ENC2/4/6` で `[0,1]` に折り込んで持つ。

アフィン変換なので、**重み和 1 の平均（ガウスぼかし・箱平均）を通しても壊れない**。
折り込んだまま拡散させ、使う直前に復号できる。

あわせて組み込みエフェクトの `D2D1_PROPERTY_PRECISION` に 16bit float を要求している。
カスタムエフェクトは入力から精度を継ぐので、そこで上げれば下流にも伝わる。
効けばフル画質、効かなくても折り込みのおかげで破綻はしない。

### 3. 引き伸ばしの伝播は歩幅が命

**1 画素ずつ長い流線を追ってはいけない。** 鞍点の近くで隣接画素の流線が
指数的に離れ、出力が櫛状の破線になる。解像度を上げても消えない
（画素のエイリアスではなく実構造のため）。

毎パス 1 歩上流だけを見て受け継ぐ形にすると、バイリニア補間が発散を抑えるので縞が出ない。
ただし **1 歩が大きいと縞が戻る**。プロトタイプでの実測:

| 1 歩 | 縞 |
| --- | --- |
| 0.9px / 1.5px | 出ない |
| 2px | わずかに出る |
| 3px 以上 | はっきり出る |

`flow_length=140` なら 93 パス。解像度を落とせば 1 パスは安くなるが、
運ぶ色の解像度も落ちるので帯の中身が眠くなる。**等倍・1 歩 1.5px** にした。

必要なパス数は `流線の長さ ÷ 1.5px`。UI の **ステップ数**（既定 192）がこれを上限で抑えるので、
長い流線では上げる必要がある。足りないと 1 歩が粗くなって縞が戻る。

### 3b. 色を拾う位置は φ の尾根まで登る

輪郭ちょうどは線画の色なので、少し上流（面の側）から色を拾う。
ここを**固定距離**にしてはいけない。

`conf` は輪郭のスケール（`輪郭の細かさ` が決めるオクターブの σ）ぶん太い帯になる。
帯の外縁にいる画素は数 px 上流を見ても**まだ背景の上**なので、
「背景色を運ぶ強い種」になって本来の輪郭色を塞ぐ。文字に掛けて実測したところ、
**優先度の高い画素の 58% が背景色を拾っていた**。帯が眠くなる原因はこれだった。

代わりに上流を 4 点見て、**φ（輪郭密度）の尾根の色**を拾う。

- 帯の外縁にいる画素は、登り切った先＝輪郭の芯で色を拾う
- すでに尾根にいる画素（＝構造の内側）は**自分の色のまま**になるので、
  文字や線画の面が背景色で塗り潰されない

ここで **argmax（1 点を選ぶ）にしてはいけない**。隣接画素で選ばれる点が切り替わり、
細かい縞が出る（合成テスト画像で縞の検出値が 0.0089 → 0.0249 に跳ねた）。
**「自分より φ が高いぶん」で重み付けした平均**にすると空間的に滑らかになり、
それでいて尾根の色が支配的になる。登り先が無ければ重みが全部 0 になり、自分の色が残る。

    w = saturate((φ_i − φ_自分) * 6)² 、自分には基礎重み 0.02

実測（合成画像の縞 / 文字の帯の明るさ）:

| | 縞 | 帯の明るさ |
| --- | --- | --- |
| argmax | 0.0249 | 36.2% |
| 重み付け平均 | **0.0160** | **37.7%** |

縞が消えたうえに帯はむしろ明るい。

探索距離は `max(ユーザー指定, 2σ_edge)`。σ_edge はオクターブ重みの重心から出す。
UI の `色を拾う位置` はその下限として働く。

色はここで**ストレートに戻して**運ぶ。プリマルチプライのまま運ぶと、
半透明の縁から拾った色がそのぶん暗くなり、不透明で塗る帯が濁る。

### 4. スコア 1 本で距離も兼ねる

リファレンスは「輪郭の強さ」と「伝播距離」を別々に運び、
`強さ - tie*距離` で比較している。RGBA では色で 3 本使うので 1 本しか残らない。

`score = 強さ - tie*距離` をそのまま A に入れれば比較には足りる。
1 歩ぶんのペナルティは定数（`(0.03 + 近さを優先×(1-gate)) / パス数`）なので、
上流の score から引くだけでよい。到達距離の上限はパス数そのものが担保する。

塗る／塗らないの閾値は、最小ペナルティの半分ぶんだけ下げて補正する（`gate - 0.015`）。
「近さを優先」のぶんは引かない。引くと上げるほど塗る範囲が広がってしまう。

### 4b. 優先度は飽和させない

`conf` はソフト閾値なので、膝を超えた輪郭はすべて 1.0 に飽和する。
`conf^1.2` だけを優先度にすると**どの輪郭も同点**になり、同点は上の距離ペナルティで
決まるので、**一番外側の輪郭が外側を丸ごと取る**。内側の輪郭を画面で一番強い輪郭に
してもその色は 1px も外へ出ない（実測）。

そこで輪郭の「強さ」を優先度に残す。GPU 側で要るものが 3 つある。

1. 強さそのもの。`Confidence` の **`.a` が空いていた**ので `強さ×conf` を載せる。
   このテクスチャは拡散側でもぼかされるが、`.a` は誰も読まないので害はない。
2. 帯の幅で均したもの。画素ごとの強さのまま競わせると、隣り合う画素が別の輪郭に
   当たって櫛状の縞が戻る。`conf` を重みにした平均（`blur(強さ×conf) / blur(conf)`）に
   すれば「この輪郭の強さ」になり、しかも単純な平滑化と違って帯の山が削れない。
   → `Confidence` に `Border → Blur → Crop` をもう 1 本生やす。
3. 画面平均。強さを絶対値で持つと、正規化の係数がずれた素材で強さが丸ごと上下し、
   届く距離まで変わる。平均との比にすれば係数は約分されて消える。
   → `confQ`（1/2 に落とした `Confidence`）から `Scale(0.5)` を 1x1 まで重ねる。

`Priority` はこの 3 つを入力に取り、`conf^1.2 × (1-W + W·saturate(比×K))` を返す。
`筆の毛` はここで優先度に値ノイズを掛ける。届く距離は優先度で決まるので、
優先度をばらつかせると毛先が不揃いになる。

ノイズは**シーン座標**に固定する（力線のノイズと同じ）。素材が動いた時に
模様が泳がないようにするため。プロトタイプ側は画像の画素座標なので、
ここだけは 1:1 にならない。**位相がずれるだけで統計は同じ**なので、
プロトタイプをシーン座標に寄せる意味は無い（シーンという概念が無い）。

### 5. 力線（LIC）の正規化と粒

リファレンスは LIC のあと σ=14 のぼかし 2 枚で局所コントラスト正規化している。
等倍で 2 パス増えるので、**標準偏差を解析的に出して割る**形に置き換えた。

流線に沿って平均される有効本数はおよそ「経路長 / ノイズの粒」なので、
`std ≈ 0.5 * sqrt(粒 / 経路長)`。

経路長は**公称の長さではなく、実際に歩いた距離**を使う（歩幅は場の強さでゲートされるので、
両者は大きく変わる）。場が強くコヒーレントな所ほど長く歩き、平均される本数が増えて
分散が下がるので、そこで線が薄くなってしまう。実測の距離で割ると、
リファレンスの局所コントラスト正規化とほぼ同じ挙動になる。
歩数ループの中で `距離 += 歩幅 * ゲート` を足すだけなので、コストはゼロ。

ノイズは白色ノイズのぼかしではなく値ノイズ（ハッシュ + smoothstep 補間）で、
**シーン座標に固定**している。スクリーン座標だと素材が動いた時に線が泳ぐ。

リファレンスは LIC のあとにアンシャープも掛けている。等倍でぼかしを増やしたくないので、
代わりに**ノイズの格子を細かく**した（セル = 粒。当初は粒×2 にしていて、線が太く眠かった）。
LIC は線に沿って平均する操作なので、格子を細かくすると線を横切る向きのコントラストが上がる。

### 6. 色空間

Sa_chromablur と同じく、**入力の格納値のまま**扱う（sRGB↔リニア変換を挟まない）。
引き伸ばしは平均ではなく保持なので、色空間の違いはほぼ出ない。

### 7. アルファ

色はプリマルチプライのまま運ぶ。引き伸ばしが届いた画素は
**アルファを 1 にして上から被せる**（元のフレームと合成しない）。
不透明素材では何も変わらず、切り抜き素材では輪郭の色が外へ張り出す。

## D2D を組む上での注意

- **ぼかしは `Border(Clamp)` → `GaussianBlur(Hard)` → `Crop`** で挟む。
  そのまま掛けると画面外が透明扱いになり、フレーム縁に偽のエッジが立つ。
  `Crop` を入れるのは、矩形を毎パス確定させて座標の対応を保つため。
- **`Scale` は中心 (0,0)** に固定する。シーン座標 `p` のテクスチャ上の位置が
  `p * 倍率` になるので、等倍のシェーダから `p * 0.25` で場を読める。
- **`res` の掛け方は用途ごとに違う。** `FieldB` は素の `amp` と `res` を別々に渡し、
  変位は `amp*(0.55+0.45*res)`、発光は `amp`、力線は `amp*res` を使う。
  1 本にまとめると発光が沈み、力線が乱れた所で消えなくなる。
- **`MapOutputRectToInputRects` は浅い所では広げ、深い所では全体を要求する。**
  出力矩形を数 px 広げるだけで済む所はそうするが、
  **100 パス近く連なる伝播では全体を要求する**。広げる形だと、タイルに分けて描かれた時に
  タイルごとに違う矩形が要求され、上流の連鎖が深さぶん描き直される。
  全体なら矩形がどのタイルでも同じなので、各パスは 1 回だけ実体化される。
  解像度の違う入力（座標系が違うので広げようがない）も全体。
  どの入力を全体要求するかは定数 `c5.w` のビットマスクで渡している。
- **定数バッファは明示的な `cbuffer`** にする。ばらの global 変数だと、
  使っていない定数が最適化で落ちた時に並びがずれる可能性がある。
- **D2D のサンプリングヘルパを自前の関数の中で呼ばない。**
  エントリポイントのローカル（走査座標）に展開されうるので、
  流線をたどる部分はマクロで書いている（`Post.hlsl` / `FieldB.hlsl`）。
- **`StretchStep` はパス数ぶんインスタンスを作る**（遅延生成、上限は UI の「ステップ数」と同じ 512）。
  必要な数だけ `Composite` に繋ぎ、余りは参照されないので描画もされない。

## 検査できた所

Windows と YMM4 が無くても、次の 10 個は自動で回せる（`.github/workflows/check.yml`）。

| 検査 | 何を見るか |
| --- | --- |
| `tests/shader_inputs_check.py` | 入力の本数が csproj / シェーダ / `[CustomEffect(n)]` で一致しているか |
| `tests/params_wired_check.py` | UI に出したパラメータが Processor まで繋がっているか |
| `tests/constants_parity_check.py` | 同じ定数が prototype / HLSL / C# で一致しているか |
| `tests/shader_constants_check.py` | シェーダが読む定数スロット（`c0`〜`c5`）を C# が入れているか |
| `tests/hlsl_syntax_check.sh` | 15 本の HLSL を glslang の HLSL フロントエンドに通す |
| `tests/csharp_compile_check.sh` | YMM4 をスタブに差し替えて C# を型検査する。Vortice は nuget の本物 |
| `tests/defaults_parity_check.py` | `GpuParams` の既定値が UI の既定値と揃っているか |
| `tests/preset_smoke.py` | サンプル生成スクリプトのプリセットが今のパラメータ定義で通るか |
| `tests/edge_cases.py` | 輪郭なし・極小・各パラメータの上下限で NaN や範囲外が出ないか |
| `tests/gpu_pipeline_regression.py` | GPU で作れる形に落とした実装が参照実装とずれていないか |

後ろの 7 つは、**コンパイルが通るのに壊れている**類の事故を実際に踏んで足したもの。

- `Priority` を 1 入力から 3 入力に増やした時、csproj の `D2D_INPUT_COUNT` を 1 のまま
  置いていた。構文チェックのスタブが入力を 6 本決め打ちで宣言していたので素通りし、
  実 fxc の走る Windows ビルドで初めて落ちる状態だった。スタブを
  `D2D_INPUT_COUNT` の本数だけ宣言する形に直し、3 か所の突き合わせも足した。
- 「近さを優先」「筆の毛」を UI に足したのに、`FieldLineProcessor` 側の適用が
  丸ごと抜けていた。C# としては何のエラーも出ない（プロパティを読まないだけ）ので、
  型検査では絶対に見つからない。
- `Params` から使われていないフィールドを消した時、サンプル生成スクリプトが
  そのフィールドを渡したままで 3 プリセットが `TypeError` になっていた。

C# は `TreatWarningsAsErrors` 込みで Debug / Release とも警告 0 で通る。
`ShaderResourceLoader.Get(...)` の名前が埋め込んだ `.cso` の論理名と一致することも見ている。

**Vortice はスタブではなく本物を使う**ので、組み込みエフェクトまわりは実質検査済み。

- `Vortice.Direct2D1.Effects` の `Border` / `GaussianBlur` / `Scale` / `Crop` は
  いずれも `ID2D1DeviceContext` を取るコンストラクタを持つ。
- プロパティは**添字ではなく型つきの名前**で設定する。`SetValue` の添字の型は
  Vortice のバージョンで `int` と `uint` の間を動いていて、生の添字で書くと移植性が落ちる。
- 精度（`D2D1_PROPERTY_PRECISION`）は**列挙型**なので、`int` で渡すと D2D に弾かれる。
  `Property.Precision` と `BufferPrecision.PerChannel16Float` をそのまま渡す。
  ここは最初 `unchecked((int)0x80000007)` を投げていて、型検査で落ちて気づいた。
- カスタムエフェクト側では精度を設定していない。YMM4 の `SetValue(int, int)` からは
  列挙として渡せないため。組み込みエフェクトで上げておけば入力から継承されるので、
  `Luma` 以外の全パスに伝わる（`Luma` の入力は素材そのもので、どのみち 8bit）。

多入力（`[CustomEffect(5)]` / `(6)`）は、YMM4 公式のコミュニティプラグインが
`[CustomEffect(12)]` / `(13)` まで使っているので登録できる。
シェーダの前置き（`#define D2D_ENTRY main` と `<d2d1effecthelpers.hlsli>` だけで
`D2DGetScenePosition` と `D2DSampleInputAtPosition` を使う形）も、
リリース済みの `Sa_chromablur` が同じ形で fxc を通っている。

`FieldLineProcessor.Update` が作る定数（オクターブ重み、σ の連鎖、拡散の重み、
attract / curl / turb / radial の σ、ステップ数、`tie`、`gate` の補正、色を拾う距離）は
`prototype/gpu_sim.py` と一つずつ突き合わせて一致を確かめた。ただし**目視**であって、
自動では見ていない。片方だけ直すと黙ってずれる。

## 未確認の点

1. **YMM4 スタブが本物と食い違っていないか。** 署名は
   [公式サンプル](https://github.com/manju-summoner/YukkuriMovieMaker4PluginSamples)、
   [公式コミュニティプラグイン](https://github.com/manju-summoner/YukkuriMovieMaker.Plugin.Community)、
   リリース済みの `Sa_chromablur` から写しているが、本物の DLL とは突き合わせていない。
   `SetInput` の添字は、コミュニティプラグインがループ変数を渡しているので `int` と判断した。
2. **YMM4 が積んでいる Vortice のバージョン。** 古いと `SetValue` の添字が `int` で、
   `FieldLineGraph.Float16` の `(uint)` がコンパイルエラーになる。
   その時は `(int)` に変える（1 行）。
3. **長い `StretchStep` の連鎖で中間バッファがどれだけ積まれるか。**
   連鎖は一本道（各パスの入力は「前のパス」と「場」だけ）なので、
   D2D が中間を使い回すなら同時に要るのは数枚で済むはず。使い回さない場合は
   等倍 RGBA16F × パス数ぶん積まれるので、`FieldLineProcessor` に伝播用の
   `Scale(0.5)` を戻して 1/2 にする（眠くなるが 1 パスが 1/4 になる）。
4. **実際の絵。** シェーダは構文しか見ていない。fxc の ps_4_0 で通るか、
   GPU の出力がプロトタイプと合うかは動かすまで分からない。

   ただし C# が計算して渡す定数は、`FieldLineProcessor.Update` の式を
   そのまま写して prototype と突き合わせてある（`flow_length=170` /
   `ゲート 0.60` / `近さを優先 0.75` / `細かさ 0.30` / `拾う位置 4px` で
   パス数 113・1 歩 1.50442px・1 パスの tie 0.00292035・拾う距離 15.3217px・
   優先度のぼかし σ 7.66084・毛の粒 13.6px・補正後のゲート 0.585 が完全一致）。
   残る不確かさは「シェーダの中の演算が GPU で同じ数になるか」だけになっている。

## 動画にするときの注意

- ノイズはシーン座標固定（上記）
- 場は素材の内容だけで決まるので、素材が静止していればフレーム間でちらつかない
- `曲がり` を上げると特異点（渦の中心）が現れる。素材が動くと特異点が動いて目立つので、
  動画では `滑らかさ` をやや高め（50% 前後）にするのが安全
- 引き伸ばしの境界は二値なので、フレーム間でちらつく可能性がある。
  気になる場合は `引き伸ばし閾値` を下げて境界を輪郭から遠ざける
